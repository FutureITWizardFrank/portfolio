Incident write-ups

Each one follows the same format: what happened and what it took down, the root cause, the fix, and the follow-ups. They're in the order they happened.

Pi detector won't start

September 6, 2026. Raspberry Pi 5, Frigate, Hailo-8L.

What happened

On a fresh Frigate install, the Hailo detector crashed at startup, and Frigate ran with no object detection.

[HailoRT] [error] CHECK failed - Driver version (4.23.0) is different from library version (4.21.0)
HailoRTException: libhailort failed with error: 76 (HAILO_INVALID_DRIVER_VERSION)

Root cause

The hailo-all package from the Raspberry Pi repository installed kernel driver 4.23.0. The Frigate stable image ships HailoRT 4.21.0, and HailoRT refuses to run against a driver with a different version.

Fix

I removed hailo-all and the 4.23 kernel module, then built the 4.21.0 driver with the install script from Frigate's stable branch. /sys/module/hailo_pci/version reported 4.21.0, and the detector came up at about 10 ms per inference.

Follow-ups

  • DoneDriver version matched to the HailoRT version in the Frigate image.

Server keeps its DHCP address

September 14, 2026. Home server on Ubuntu Server.

What happened

After reboots, the server came up on a DHCP address instead of its static one. Every DNS record and bookmark pointed at the static address, so all services looked down.

Root cause

Two tools were configuring eno1. Netplan set the static address while NetworkManager kept its own DHCP profile active on the same interface, and whichever finished last at boot won. The ISP's gateway can't reserve addresses, so DHCP handed out a different one.

Fix

I gave systemd-networkd sole ownership of eno1 with a static 10-eno1.network file and marked the interface unmanaged in NetworkManager. On RHEL, a single NetworkManager profile now does the job.

Follow-ups

  • DoneOne tool owns each interface.

Containers unreachable after re-addressing

September 27 and October 6, 2026. Home server, Docker macvlan.

What happened

I moved the server behind a second router onto a new subnet, then removed that router nine days later and moved back to the original one. Both moves left containers unreachable from the host and the LAN, sites behind Caddy hung, and Seafile couldn't reach its database.

Root cause

Several separate problems showed up together:

  • A host can't reach its own macvlan containers without a shim interface. The shim's routes needed rebuilding, and my first attempts used ranges that don't start on a boundary, like a /26 starting at .25. ip route rejects those with Invalid prefix for given prefix length.
  • Seafile writes its database address into four config files on first start, so changing the compose file alone wasn't enough.
  • Pi-hole's local DNS records still pointed at the old addresses.
  • The host firewall was blocking 443 to Caddy after the change.

Fix

I recreated the macvlan network on the new subnet and gave the shim a single /32 address with one /32 route per container, so nothing depends on range alignment. I found every hard-coded old address with grep -r, replaced them with sed, updated the Pi-hole records, and opened 80 and 443.

Follow-ups

  • DoneAddress map for every container kept in the runbook.
  • DoneShim routes defined in a NetworkManager connection so they survive reboots.

Every .lan site down at once

October 10 to October 13, 2026. Home server, 8 TB USB drive.

What happened

Every https://*.lan site stopped loading, and Seafile and Jellyfin went down with them. Caddy's logs were full of input/output errors. The kernel log showed the 8 TB drive had disconnected twice on October 10. I noticed three days later.

Root cause

The enclosure uses an ASMedia bridge chip (174c:235c) with the UAS driver, a combination known for random resets. It was also connecting at USB 2.0 speed. After each reset, the kernel brought the disk back under a new device name, the old mount went stale, and Caddy could no longer read its certificates, which lived on that drive.

The disk itself looked healthy: SMART showed no reallocated or pending sectors, though it has about 59,000 power-on hours.

Fix

# use plain usb-storage instead of UAS for this bridge
sudo grubby --update-kernel=ALL --args="usb-storage.quirks=174c:235c:u"

# /etc/fstab: boot without the drive instead of hanging
UUID=...  /mnt/storage  ext4  defaults,nofail,x-systemd.device-timeout=30s  0 2

# make the empty mountpoint immutable, so nothing writes
# to the root disk when the drive isn't mounted
sudo umount /mnt/storage && sudo chattr +i /mnt/storage && sudo mount /mnt/storage

The drive dropped once more after the quirk, so the fix reduced resets but didn't end them.

Follow-ups

  • DoneMoved compose files and app state to the internal NVMe, so a drive drop no longer takes down DNS, HTTPS or the NVR.
  • DoneScheduled backups of configs and the Seafile library to the internal disk and off-site.

CPU pinned at 1,100%

October 20, 2026. Home server.

What happened

The server slowed down, and top showed rg using about eleven cores with 330 minutes of CPU time.

Root cause

rg is ripgrep, which VS Code uses for search. My Remote-SSH session was indexing a folder that contained the /opt/docker symlink, and the search followed it onto the 8 TB drive, through container data and the media library.

Fix

Closing the remote session ended the process.

Follow-ups

  • DoneSet search.followSymlinks to false and excluded /mnt/storage from search and file watching.
  • DoneRemote sessions open one stack's folder instead of my home folder.

Detection down after a nightly update

October 24, 2026. Raspberry Pi 5, Frigate, Hailo-8L.

What happened

The first run of my new daily update job installed a new kernel and rebooted the Pi. Frigate came back with HAILO_DRIVER_NOT_INSTALLED, and /dev/hailo0 was missing.

Root cause

The Hailo driver is an out-of-tree module built for one specific kernel, and the new kernel had no matching module. Reviewing the script turned up two more bugs:

  • The reboot check compared the running kernel against the newest kernel of any flavor. Pi OS installs two, rpi-2712 for the Pi 5 and rpi-v8 for the Pi 4, so the script would have seen a "new" kernel and rebooted every day.
  • An unattended apt autoremove --purge removed desktop panel plugins.

Fix

I rebuilt the driver and rebooted, then held the kernel packages with apt-mark hold. The reboot check now only compares kernels of the running flavor, and autoremove is no longer in the script.

RUNNING=$(uname -r)
FLAVOR=${RUNNING##*-}
LATEST=$(ls -1 /lib/modules | grep -- "-${FLAVOR}\$" | sort -V | tail -1)
if [ -n "$LATEST" ] && [ "$RUNNING" != "$LATEST" ]; then
  /sbin/shutdown -r +1 "Rebooting after updates"
fi

Follow-ups

  • DoneKernel held. Kernel updates are a manual procedure: unhold, upgrade, rebuild the driver, reboot, verify.
  • DoneUpdate script fixed and logging to /var/log/auto-update.log.

Invalid certificate signature

October 25, 2026. Raspberry Pi 5, Caddy.

What happened

After I added HTTPS to the Pi, Firefox refused the page with Peer's certificate has an invalid signature. The usual "accept the risk" button wasn't offered.

Root cause

Both Caddy servers had generated a private CA with the same default name. My laptop already trusted the home server's, so Firefox matched the Pi's certificate to that root by name, checked it against the wrong key, and failed.

Fix

I gave the Pi's CA its own name in Caddy's global options, deleted the old CA data so Caddy would generate a new one, and imported the new root on my devices.

{
    pki {
        ca local {
            name "Pi Local CA"
            root_cn "Pi Local CA - Root"
            intermediate_cn "Pi Local CA - Intermediate"
        }
    }
}

Follow-ups

  • DoneThe Pi's CA has its own name, so it can't collide with the home server's.
